<objective>
Close UAT gap G-01-6: HTTPS downloads fail in the notarized macOS bundle (and in the Linux bundles on hosts without Debian's /usr/lib/ssl) because the frozen OpenSSL's CA location is a compile-time path on the CI runner and porter passes no SSL context, so 0 CAs load (root cause in .planning/debug/macos-bundle-tls-cert-verify.md, binding).

Purpose: the Setup tab's Download missing tools and `--fps60` work for a tester on any supported host (PKG-02 macOS, PKG-03 and PKG-04 Linux, whose floor names Fedora 40+). The rule lives in porter/ (the GUI holds no pipeline logic) as one context that falls back to the host's own CA file only when the default store is empty. Standard library only: no new dependency. truststore would read the macOS keychain, but it adds a locked runtime dependency, it was never run inside the signed hardened-runtime app (its macOS path calls Security.framework through ctypes), and the debug session's positive control already proved that the signed app verifies dl.google.com with Apple's /etc/ssl/cert.pem. No process-wide SSL_CERT_FILE, because .NET on Linux honours it in the translator's NuGet restore and every child would inherit it.
Output: porter/tls.py, one-line hooks in the upstream files porter/fetch.py and porter/fpslocker.py, tests/test_tls.py with its fixture.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| porter → dl.google.com, builds.dotnet.microsoft.com, raw.githubusercontent.com | Download lists, toolchain archives and FPSLocker configs cross the network; TLS verification is what makes the lists' checksums trustworthy |
| host CA files → porter's SSL context | Trust anchors read from root-owned system paths on the player's machine |
| porter → child processes (dotnet, clang, adb, the engine tools) | Children inherit porter's environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-28 | Spoofing / Tampering | porter/tls.py context() | high | mitigate | The fix only adds trust anchors to ssl.create_default_context() (CERT_REQUIRED, check_hostname), never builds an unverified context and keeps verifying when no CA file exists; test_no_host_file_stays_verifying asserts CERT_REQUIRED and check_hostname True. The archives' SHA-1/SHA-512 checks in fetch._download stay as they are |
| T-1-29 | Elevation of Privilege / Tampering | process environment | medium | mitigate | No SSL_CERT_FILE or SSL_CERT_DIR is set: the CA file reaches only porter's own urlopen calls through context=, so dotnet's NuGet restore and the other children keep their own trust; test_environment_untouched asserts the environment is unchanged |
| T-1-30 | Tampering | CA_FILES host paths | low | accept | The paths are root-owned system files (/etc/ssl, /etc/pki); a user who can write them already controls the host's trust store. They are read only when the default store is empty, so a working default never gains anchors |
| T-1-31 | Repudiation / Tampering | a future urlopen without the context | low | mitigate | test_every_urlopen_passes_the_context scans porter/*.py on all four CI hosts, so a new download path cannot silently go back to the empty store |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed or added: standard-library ssl only; requirements*.in and the hashed locks are unchanged |
</threat_model>
